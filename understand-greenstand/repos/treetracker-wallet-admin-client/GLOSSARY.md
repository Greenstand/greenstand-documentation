## Domains

### Authentication & Access

Authentication & Access handles the login of a wallet owner with a wallet name, a password, and an API key. It keeps the session (the auth token and the wallet identity) in the browser and guards the protected pages. It also ends the session at logout.

**Terms:** Credentials, Auth token (JWT), Wallet identity, API key, Session

**Rules:**

- The login form needs a wallet name and a password. Without them, the LOG IN button stays disabled.
- The form shows an error for a wallet name over 150 characters. It shows an error for a password or an API key over 50 characters. These errors do not stop the login request.
- The client sends the API key in the TREETRACKER-API-KEY header. It sends the auth token with the Bearer scheme.
- The REACT_APP_WALLET_API_ROOT variable sets the wallet API root for all calls. The build script reads it from .env.production. The build:test script reads it from .env.test. The build:dev script and the start script read it from .env.development.
- The client always stores the wallet identity. It stores the auth token only when Remember me is on.
- At page load, the user counts as logged in only when the browser has a stored auth token and a stored wallet identity.
- A failed login removes the stored API key.
- Logout removes the stored auth token, the stored wallet identity, and the stored API key.
- The client keeps the expiration value of the auth token. It does not check this value.

**Flows:**

- **User Login** (`POST {REACT_APP_WALLET_API_ROOT}/auth from the /login form`): A wallet owner enters a wallet name, a password, and an API key on /login. The client posts the credentials to the auth endpoint and receives an auth token. It decodes the wallet identity from the auth token, saves the session, and opens the home page.
- **Restore Session and Guard Routes** (`App start and each navigation to a protected route`): At page load, the auth provider rebuilds the session from localStorage. The route table lets only a logged-in user open the protected pages. The shared API client adds the API key and the auth token to the wallet API calls.
- **Logout & Session Expiry** (`Logout icon in the top bar, a missing stored wallet identity, or a 401 answer`): The session ends when the user clicks the logout icon or when a page finds no stored wallet identity. Logout clears the stored session and opens /login. For a 401 answer, the client tries to open /login, but that code cannot work.

### Wallet Management

Wallet Management shows the logged-in wallet with its balance and its pending transfers. It lists the wallets that the wallet owner can see, by scope. It also creates managed wallets from the My Wallets page or from the Send Tokens page.

**Terms:** Wallet, Managed wallet, Child wallet, Wallet balance, Pending transfer count

**Rules:**

- My Wallets starts with the child scope. The user can change the scope to all wallets or managed wallets.
- A scope change sends the table back to the first page.
- The wallet table sorts by created date, newest first, by default. The user can sort by name or by created date.
- The wallet table shows 10 or 50 wallets on a page.
- A new managed wallet name can contain only letters, digits, and the - . @ characters.
- The My Wallets dialog needs a name of at least 3 characters. The Send Tokens inline field does not check a minimum length.
- The home page shows the display name of the wallet. If the display name is not set, it shows the wallet name.
- The home page counts all pending transfers in the API answer. It does not filter them by direction.

**Flows:**

- **View Wallet Home** (`Open / (Home)`): The home page (/) loads the logged-in wallet and the pending transfers. It shows the wallet logo, the name, the pending transfer count, the about text, and the token balance.
- **Browse My Wallets** (`Open /list-wallets (My Wallets)`): My Wallets (/list-wallets) shows a paged, sortable table of wallets. The user picks a wallet scope: all, child, or managed. Each change of page, sort, or scope loads the wallets again from the wallet API.
- **Create Managed Wallet** (`Create Managed Wallet button on /list-wallets, then POST /wallets`): On My Wallets, the user opens a dialog and enters a name for a new managed wallet. The client checks the name and posts it to the wallet API. After success, the dialog shows a success view and the wallet table loads again.
- **Create Managed Wallet from Send Tokens** (`+ Create Managed Wallet link on /send-tokens (Managed Wallets tab), then POST /wallets`): On the Managed Wallets tab of Send Tokens, the user can create a managed wallet inline. The page posts the new name to the wallet API and shows a result message. Then the receiver selector tries to select the new wallet.

### Token Transfers

Token Transfers moves tokens from a sender wallet to a receiver wallet. The Send Tokens page has three receiver tabs: Managed Wallets, Trusted Wallets, and All Wallets. The My Transfers page lists transfers and lets the user accept, decline, or cancel a pending transfer.

**Terms:** Transfer, Pending transfer, Token amount, Sender wallet, Receiver wallet, Available tokens

**Rules:**

- The sender list holds child wallets and the logged-in wallet. It shows at most 10 child wallets that match the typed text.
- The available tokens are the wallet balance minus the pending outgoing amount.
- The token amount must be more than 0. It must not be more than the available tokens.
- The submit button stays disabled until the form has a sender, a receiver, and a valid amount.
- The user must confirm each transfer in a dialog.
- Each transfer request sends claim as false.
- The Managed Wallets tab offers child wallets as receivers.
- The Trusted Wallets tab offers only the target wallets of trusted send relationships. In these relationships, the sender wallet is the actor.
- The All Wallets tab accepts any receiver name. It suggests the wallets of all trusted relationships of the logged-in wallet.
- Only a pending transfer opens the side panel.
- The user can accept or decline a pending transfer when the receiver is the logged-in wallet or one of its child wallets.
- The user can cancel a pending transfer when the sender is the logged-in wallet or one of its child wallets.
- The status filter offers Pending, Completed, and Cancelled. The date filter does not accept future dates.
- The menu badge counts pending transfers to the logged-in wallet or its child wallets. The badge shows only when the side menu is open.

**Flows:**

- **Send Tokens to a Managed Wallet** (`/send-tokens, Managed Wallets tab, then POST /transfers`): On the Managed Wallets tab of /send-tokens, the user picks a sender wallet and a child wallet as receiver. The page shows the balance, the pending amount, and the available tokens of the sender. After an amount check and a confirm dialog, the page posts the transfer.
- **Send Tokens to a Trusted Wallet** (`/send-tokens, Trusted Wallets tab, then POST /transfers`): On the Trusted Wallets tab of /send-tokens, the receiver list holds only wallets that the sender wallet trusts for send. The page reads all trusted relationships of the sender and keeps the send relationships where the sender is the actor. The transfer then uses the same form, check, and post as the Managed Wallets tab.
- **Send Tokens to Any Wallet** (`/send-tokens, All Wallets tab, then POST /transfers`): On the All Wallets tab of /send-tokens, the user can type any receiver wallet name. The field suggests every wallet that has a trusted relationship with the logged-in wallet. The page posts the transfer and warns that the receiver is not trusted.
- **Browse Transfers** (`Open /my-transfers (My Transfers)`): My Transfers (/my-transfers) shows a paged table of transfers with status and date filters. The table sorts by created date, closed date, or status. It marks pending transfers that wait for an answer from the user.
- **Act on a Pending Transfer** (`Click on a pending row on /my-transfers, then POST /transfers/{id}/accept, POST /transfers/{id}/decline, or DELETE /transfers/{id}`): A click on a pending transfer opens a side panel with its details. The receiver side can accept or decline the transfer, and the sender side can cancel it. After the action, the transfer list and the pending count load again.

### Trust Relationships

Trust Relationships lets a wallet owner request a trust relationship between a requesting wallet and a target wallet. The Trust Relationship page lists the relationships of the logged-in wallet with search and filters. A side panel lets the user accept, decline, or delete a relationship.

**Terms:** Trust relationship, Relationship request, Relationship type, Request type, Relationship state, Trusted wallet

**Rules:**

- A request needs a request type, a requesting wallet, and a target wallet name.
- The target wallet name must have at least 3 characters. It can contain only letters, digits, and the - . @ characters.
- The request type list holds manage, send, deduct, receive, release, and yield.
- The type filter holds manage, send, and deduct.
- The list sorts by state in descending order by default.
- The search text goes to the API as a lowercase search filter.
- The user can accept or decline a requested relationship when the target is the logged-in wallet or one of its child wallets.
- The user can delete a trusted relationship. The user can also delete a requested relationship when the target is not the logged-in wallet or one of its child wallets.
- A cancelled relationship shows no action.
- The menu badge counts requested relationships to the logged-in wallet or its child wallets.

**Flows:**

- **Request Trust Relationship** (`+ Create button on /trust-relationship, then POST /trust_relationships`): On the Trust Relationship page, the user opens a dialog to request a trust relationship. The user picks a request type and a requesting wallet and types a target wallet name. The client checks the fields, posts the request, and reloads the list.
- **Browse Trust Relationships** (`Open /trust-relationship (Trust Relationship)`): The Trust Relationship page (/trust-relationship) lists the trust relationships of the logged-in wallet in a paged table. The user can search by wallet and filter by state, request type, and type. The table marks requests that wait for an answer from the user.
- **Act on a Trust Relationship** (`Click on a row on /trust-relationship, then POST /trust_relationships/{id}/accept, POST /trust_relationships/{id}/decline, or DELETE /trust_relationships/{id}`): A click on a trust relationship opens a side panel with its wallets and its request type. The target side can accept or decline a request. The user can delete a trusted relationship. The user can also delete a request when the target is not one of the user's wallets. After the action, the list and the pending count load again.

### Wallet Customization

Wallet Customization lets the wallet owner change how the logged-in wallet looks. The owner edits the display name and the about text and uploads a logo and a hero image. Each change goes to the wallet API as a wallet update.

**Terms:** Wallet profile, Display name, About text, Logo image, Hero image

**Rules:**

- A display name must have at least 2 characters.
- The about text must have at least 5 characters when the formatting tags are removed.
- A logo must be a square PNG or JPG image of 1 MB or less.
- A hero image must be a PNG or JPG image of 1 MB or less. Its width must be at least two times its height.
- The page uploads an image directly after the image passes the checks.
- Each save sends the display name and the about text that the page loaded. Only the changed field has a new value.
- Messages close after 3 seconds.

**Flows:**

- **Update Display Name and About Text** (`Save buttons on /customize-wallet, then PATCH /wallets/{id}`): On /customize-wallet, the user edits the display name and the about text of the logged-in wallet. Each field has its own check and its own Save button. A save sends a wallet update to the wallet API.
- **Upload Logo and Hero Image** (`Upload buttons on /customize-wallet, then PATCH /wallets/{id}`): On /customize-wallet, the user uploads a logo and a hero image for the logged-in wallet. The page checks the file type, the size, and the shape. Then it sends the file at once in a wallet update.
